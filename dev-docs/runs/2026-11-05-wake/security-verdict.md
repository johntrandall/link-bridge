# Security verdict: /wake and POST /act/wake (link-bridge 0.1.15)

Checked cold in a detached worktree of 8b3736d, on a scratch bridge at 127.0.0.1:5493 (my own PID, killed afterwards). Concurrency and grammar probes used a fake `WATCHBILL_BIN_PATH` that logs its argv and sleeps 3 s; the 409/403 probes used the real `~/.local/bin/watchbill` 0.10.95. Confidence marks: **Verified** means I ran it; **Inferred** means I read it and did not run it. Two items block (5, 2), and two are small required fixes (1, 7).

**1. Argument safety: no shell, no option injection, but the grammar check is not ASCII (fix required, not exploitable).** `run_wake` passes a fixed argv list to `subprocess.run` (bin/link-bridge:397-400): no shell, and `SLUG_RE` (:381) requires a leading `[a-z0-9]`, so a name can never become a watchbill option. Verified: `-x`, `a b` and `a;b` answer 400. However, `SLUG_RE` is compiled with `re.IGNORECASE` on a str pattern, which in Python means Unicode case folding, so `[a-z]` also matches U+212A KELVIN SIGN, U+0130 İ and U+017F ſ. `.lower()` (:397) then runs after the check. Verified on the scratch bridge: `"Kelvin"` reached watchbill as `kelvin`; `"ſystem"` reached it as non-ASCII `ſystem`; and 64 × `İ` reached it as a 128-character non-ASCII argument (`i̇` × 64), twice the stated maximum. This is harmless to safety (no shell, no dash, and watchbill refuses an unknown system), but the server does not enforce the slug grammar the README and the comment at :375 claim, and it disagrees with the page (wake.js:14 `/i` without `u` is ASCII-only). Fix: `re.compile(r"[a-z0-9][a-z0-9._-]{0,63}", re.IGNORECASE | re.ASCII)`, or lower first and match without IGNORECASE, plus a test with `"K"`.

**2. Request gates: the header gate does not cover DNS rebinding (FAIL for an action that starts an agent).** No `do_OPTIONS` exists, so a preflight answers 501 (Verified: `OPTIONS /act/wake` with Origin and Access-Control-Request-Headers returned 501), and a cross-origin fetch carrying `X-Link-Bridge` never goes out. A missing header answers 403 (Verified, :132-134). The body is capped at 4096 bytes before any read (:139). `GET /act/wake` answers 404, so a GET has no side effect (Verified). The CSP on /wake is `connect-src 'self'; form-action 'none'; frame-ancestors 'none'` plus `X-Frame-Options: DENY` (Verified with `curl -I`; HEADERS :51-59). Not requiring `Content-Type` is fine: a form or a simple request cannot set the custom header. The gap is that `do_POST` (:125-156) never checks `Host`. Verified: `POST /act/wake` with `Host: evil.example:5493` and the header was accepted and ran watchbill (409 from watchbill). A page served from an attacker's hostname that rebinds to 127.0.0.1 is same-origin with itself, so it can send `X-Link-Bridge: 1` with no preflight and POST `{"system":"<a guessable system>"}` to port 5465. This defeats the claim in the comments at :119-120 and onmac.js:4-5 that "a page on another origin cannot trigger an action". The browser side is Inferred: Chrome's Local Network Access prompt likely stops it, Safari has no equivalent I know of, and system names are guessable (`link-bridge`, `watchbill`). The impact is waking any asleep seat of John's: an agent, credits, a "John asked for you" first prompt. The cost of the fix is a few lines. Fix: in `do_POST`, before the header check, answer 403 unless `self.headers.get("Host")` is in an allowlist: `link.localhost`, `127.0.0.1:<port>`, `localhost:<port>`, `[::1]:<port>`, and the tailnet names Tailscale Serve presents (`susanbones:5465`, `susanbones.flicker-duckbill.ts.net:5465`; `tailscale serve status`), configurable by an env var. Add a test that a foreign Host answers 403. This protects every /act/ action, not only /act/wake.

**3. The page: nothing fires on load, and the command shown is the command run (pass).** `render` (wake.js:58-73) only sets text and calls `wireOnMac`, which assigns `onclick` and does not fetch (onmac.js:20-38). `hashchange` (:76) only re-renders. An invalid fragment hides the button (:66). Verified: headless Chrome loaded `/wake#link-bridge/lead-designer` against the scratch bridge; the log shows only GET /wake, /bridge.css, /onmac.js and /wake.js, and the fake watchbill was called 0 times. My screenshot shows the command and the one button. The displayed command (wake.js:49) uses the same lowercased names the payload carries, and the server runs `[WATCHBILL_BIN, "resume", system, "--seat", seat]` (:397); they differ only in the absolute path of watchbill. The default seat is `lead-designer` on both sides (wake.js:44, :390).

**4. Reachability on the tailnet without a login check (acceptable once items 2 and 5 are fixed).** Any tailnet device can press the button, and `Tailscale-User-Login` is read only for registered actions (:153-155). I judge the existing policy, the same gates as /act/herdr-jump, sufficient here for these reasons. The request chooses only two slugs. watchbill decides everything else: it refuses an unknown system (Verified, 409 "no system …") and anything not asleep (watchbill:2126-2132), and `wake()` refuses a live seat (watchbill_sleep.py:520-521) and one past its hard line (:524-525). The woken seat resumes its own recorded conversation, brief, model and permission mode in John's herdr, and the requester cannot inject a prompt, because the first prompt is fixed by watchbill (watchbill:2141). The worst a tailnet device can do is start a seat early, at a cost in credits. That is the level of /act/herdr-jump with a bill attached, not code execution. A token would add friction to the one place it is used (an Obsidian row) for little gain. Recommended, not blocking: log `Tailscale-User-Login` (or "loopback") to stderr on each /act/wake, because watchbill's first prompt tells the seat "John asked for you" whoever pressed.

**5. The subprocess: a repeated click can spawn twice (FAIL).** `TOOL_PATH` (:385) prepends fixed directories to the inherited PATH, and the `env` inheritance (:400) is the brew service's own environment. Neither is reachable from the request. The 120 s timeout (:399) is shorter than watchbill's own spawn budget: `run_wake` gives herdr-lifecycle 240 s, then sleeps 3 s and types the first prompt (watchbill_sleep.py:465-489). So on a slow spawn the bridge kills watchbill after herdr-lifecycle has started the seat, and the seat runs without its first prompt and without the `woke` ledger row (:539). That last point is Inferred from reading. Fix: 300 s. The blocking finding is the "second resume refuses" reasoning, which holds only for clicks spaced wider than a spawn. Nothing serializes two wakes: the server is a `ThreadingTCPServer` (:171), `run_wake` takes no lock, onmac.js:26-38 does not disable the button during the fetch, and watchbill holds no lock either. `cmd_resume` reads the ledger and snapshots herdr (watchbill:2125-2136); `wake()` checks liveness against that snapshot (watchbill_sleep.py:520); herdr-lifecycle refuses a duplicate name only once the first session is registered live (herdr-lifecycle:1914-1916); and the `woke` row is written after the spawn (watchbill_sleep.py:539). Verified on the bridge side: two concurrent POSTs started two `resume link-bridge --seat lead-designer` processes 2 ms apart, and both answered 200. Inferred on the watchbill side: a double click (or a click plus the board daemon) inside the spawn window resumes the same session twice, which gives two live lead designers on one conversation. Fix in the bridge: a module-level `threading.Lock` acquired non-blocking in `run_wake`, answering 409 "a wake is already running", plus a per-(system, seat) cooldown of about 60 s after a 200. On the page: disable the button on the first click. Add a test of two concurrent POSTs with a sleeping fake watchbill, in which one answers 409.
